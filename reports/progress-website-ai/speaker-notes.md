# ความคืบหน้า Website / AI — ฉบับแก้ไข

19 สไลด์; ภาพรวม 1–2, Website 3–8, AI 9–18, สรุป 19

หน้า 4 มีช่องรูป 2 ช่องสำหรับใส่ภาพเอง; โค้ดบางส่วนย่อและจัดบรรทัดจากโปรเจ็กต์ ไม่ใช่ฟังก์ชันที่รันเดี่ยวได้

## 1. รายงานความคืบหน้า Website และ AI

แนะนำโครงงานและผู้จัดทำ รายงานแบ่งสองช่วงคือ Website และ AI โดยเริ่มจากความคืบหน้าปัจจุบันก่อนงานค้าง เว็บไซต์สำหรับผู้ใช้หุ่นเรียกว่า Robot Interface ในสไลด์ชุดนี้ มีช่องภาพให้ผู้จัดทำเติมเองและตัวอย่างโค้ดที่ย่อจากโค้ดจริง ไม่มีการทดลองหุ่นหรือโมเดลใหม่ระหว่างจัดทำ



## 2. ความคืบหน้าปัจจุบัน แยกเป็น 2 ฝั่ง

Website มีสองหน้าใช้งาน Backend และฐานข้อมูล แสดงแผนที่จัดการ POI และมีคำสั่งควบคุมแล้ว งานที่ยังค้างคือเส้นทางอัปโหลดแผนที่ แก้ไขแผนที่รวมกำแพงเสมือน และการเชื่อมโหมดหุ่น ส่วน AI วิธีหนึ่งและสองทำแล้วบน PC มีชุด regression 40 กรณี ส่วนวิธีสาม Jetson และเสียงยังค้าง ไม่ใช้คะแนน benchmark เป็นเปอร์เซ็นต์ความสำเร็จของโครงการ

หลักฐาน: PROGRESS.md; maps.ts; robotIntent.ts

## 3. ช่วงที่ 1 — ความคืบหน้าฝั่ง Website

ช่วง Website เริ่มด้วยหน้าที่ของเว็บไซต์ทั้งสองฝั่งและพื้นที่ภาพหน้าจอ ต่อด้วยคำอธิบายเส้นทางคำสั่ง Backend ข้อมูลแผนที่และ POI ก่อนสรุปงานค้างที่ผู้จัดทำระบุคืออัปโหลด แก้ไขแผนที่ กำแพงเสมือนและโหมดของหุ่น การมีปุ่มหรือ API ยังไม่เท่ากับผ่านการตรวจรับอุปกรณ์



## 4. เว็บไซต์ทั้ง 2 ฝั่ง: หน้าที่และความคืบหน้า

Admin Website ใช้โดยเจ้าหน้าที่หรือผู้ดูแลสำหรับดูสถานะ แผนที่ ควบคุมและจัดการจุดหมาย รวมถึงดูงานและบัญชีตามสิทธิ์ Robot Interface ใช้โดยผู้มาเยือนหรือผู้ใช้หุ่น สำหรับเลือกจุดหมาย พิมพ์คำขอ AI ดูงานและยกเลิกงานของตนเอง จุดส่วนตัวถูกกรองจากหน้าใช้งานผู้มาเยือน ช่องสีเทาทั้งสองช่องเป็นรูปทรงแก้ไขได้สำหรับนำภาพหน้าจอมาใส่ ไม่ใช่ภาพหน้าจอจริง

หลักฐาน: apps/admin; routes/robot.ts; services/chatService.ts

## 5. เมื่อผู้ใช้กดสั่งงาน ข้อมูลเดินทางอย่างไร

หนึ่ง ผู้ใช้กดจาก Admin หรือ Robot Interface ส่ง REST request ถึง Backend สอง Backend ตรวจ session หรือ device token บทบาท งาน lock และความพร้อมของแผนที่ สาม บันทึกงานเหตุการณ์ลงฐานข้อมูลเมื่อใช้งานจริง สี่ สั่งหุ่นผ่าน REST adapter ห้า รับข้อมูลหุ่นกลับแล้วส่งสถานะไปเว็บด้วย Socket.IO พร้อม HTTP fallback แหล่งเก็บข้อมูลต่างจากตัวหุ่น เว็บไซต์จึงไม่ยิงคำสั่งฮาร์ดแวร์โดยตรง

หลักฐาน: app.ts; middleware/auth.ts; jobService.ts; ws/socket.ts; prisma/schema.prisma

## 6. แผนที่ POI และการควบคุม: ทำส่วนไหนแล้ว

แผนที่สดมี grid หุ่น home POI และ LiDAR ซูมและลากได้ จุดหมายเพิ่มแก้ลบและใส่ aliases ได้พร้อมอ่านกลับยืนยัน มี joystick นำทาง กลับแท่นและหยุดที่ผ่านสิทธิ์และ lock การแก้จุด POI ไม่ใช่การแก้ occupancy map หรือกำแพงเสมือนบนหุ่น ผลการอ่านอุปกรณ์เคยตรวจแล้ว แต่การถึงจุดหมายและการหยุดจริงยังรอตรวจรับ

หลักฐาน: LiveRobotMap.tsx; RobotMapEditor.tsx; jobService.ts; navigationPolicy.ts

## 7. Website: งานที่ยังค้างอยู่

งานค้างตามที่ผู้จัดทำระบุมีสามกลุ่ม: อัปโหลดหรือใช้ไฟล์แผนที่ร่วมกับหุ่น แก้ไขแผนที่รวมวาดกำแพงเสมือน และเชื่อมโหมดของหุ่น ในโค้ดเดิมมี import JSON ไป draft และเก็บ keepout polygons แต่ไม่ถือว่าเส้นทางอัปโหลดหรือแก้ SLAM map และกำแพงเสมือนบนหุ่นเสร็จแล้ว ต้องเชื่อม API ใช้กับ navigation และอ่านกลับยืนยันจริง

หลักฐาน: maps.ts; mapImportSchema; RobotOperatingMode.tsx; SPEC.md

## 8. หลักฐานฝั่งระบบเว็บและ Backend

ผล Backend ล่าสุดที่บันทึกไว้ผ่าน 52 tests เป็นจำนวนรวมทั้งระบบ ไม่ใช่ฝั่งเว็บเพียงอย่างเดียว typecheck ผ่าน Admin Robot Interface และ Backend ครอบคลุมสิทธิ์ API เซสชัน งาน แผนที่ POI และการตรวจคำขอ AI ผลอ่านแผนที่ตำแหน่งและ LiDAR จริงเป็นหลักฐานรอบก่อนหน้า ยังไม่อ้างผลเดินจริงหรืออัปโหลดกำแพงเสมือนจริง

หลักฐาน: PROGRESS.md; apps/backend/test; scripts/check-robot-live.mjs

## 9. ช่วงที่ 2 — ความคืบหน้าฝั่ง AI

AI ปัจจุบันใช้ Qwen3.5-2B Q5_K_M บน PC ผ่าน llama-server ยังไม่ใช่ Jetson เนื้อหาต่อไปอธิบายเทคนิคที่ทำแล้ว ได้แก่กฎและ aliases โมเดลคืน structured JSON และ backend validation พร้อมโค้ดบางส่วนที่จัดบรรทัดเพื่ออ่านง่าย บริบทถามตอบคำสั่งข้ามข้อความและระบบเสียงยังเป็นงานค้าง



## 10. เทคนิคที่ใช้: Hybrid intent classification

เป็น hybrid intent classification: ตรวจภาษาและจับชื่อก่อน ถ้าคำขอชัดใช้กฎเพื่อลดการรอ หากรูปประโยคอ้อมให้ LLM ตีความ โดยให้เลือก UUID จากรายการปลายทาง และให้ Backend ตรวจอีกชั้น ไม่ได้ใช้ embeddings vector search หรือ fuzzy matching ในการจับชื่อปัจจุบัน ทั้งสองเทคนิคทำแล้ว ไม่ได้ fine-tune โมเดลใหม่

หลักฐาน: robotLanguage.ts; robotIntent.ts; robotAiService.ts

## 11. ขั้นตอนจริง: ข้อความ → เจตนา → งานนำทาง

Robot Interface ส่งข้อความ ขั้นแรก normalize และวิเคราะห์ speechAct กับชื่อจุดหมาย คำหยุดที่รองรับเข้าทางลัด ถัดไปกฎหรือโมเดลคืน intent confidence poiCode speechAct needsClarification จากนั้นตรวจ schema รหัสและความกำกวม ก่อนอ่านแผนที่ใหม่และสร้างงาน เฉพาะกรณีผ่านข้อกำหนด หากเป็น dry-run จะคืนผลอย่างเดียว ไม่สร้างงาน

หลักฐาน: robotIntent.ts; robotAiService.ts

## 12. เทคนิค 1: Normalize + Regex + POI aliases

normalize ใช้ NFC เพื่อคงรูปสระภาษาไทย จากนั้นใช้ regular expressions ตรวจคำขอ คำถาม คำปฏิเสธ สมมติและข้อความยกมา matchRobotDestinations เทียบชื่อและ aliases ตรวจขอบเขตชื่ออังกฤษ และเลือกชื่อเฉพาะกว่าที่ทับตำแหน่งเดียวกัน กรณีชื่อซ้ำจะไม่เดา โค้ดที่เห็นเป็นส่วนของ classifyRobotTranscript ที่จัดบรรทัดใหม่ ไม่ใช่ฟังก์ชันที่รันเดี่ยวได้

หลักฐาน: robotLanguage.ts; robotIntent.ts

## 13. เทคนิค 2: บังคับรูปแบบ JSON และตรวจด้วย Zod

LLM มี closed set ของ intent และ poiCode ที่อยู่ใน catalog คำสั่งกำหนด JSON Schema เพื่อให้โมเดลตอบตามรูปแบบ และใช้ Zod ตรวจชนิดและช่วงคะแนนอีกครั้ง โค้ด outputSchema เป็น excerpt ที่จัดบรรทัดจากของจริง strict ไม่ให้เพิ่มฟิลด์อื่น confidence เป็นคะแนนจากโมเดล ไม่ใช่สิทธิ์ให้เดินเอง

หลักฐาน: robotIntent.ts: outputSchema / schema

## 14. การเรียกโมเดล: Prompt + Schema + ค่าควบคุม

Backend เรียก llama-server ผ่าน endpoint chat completions ซึ่งรัน Qwen บน PC prompt อธิบายคำขอสุภาพ คำถาม สมมติ และปฏิเสธ พร้อมรายชื่อ/aliases ของ POI ใช้ temperature 0 seed 42 max tokens 256 และปิด thinking โดยส่ง schema ไปด้วย seed และ temperature ช่วยลดการสุ่มแต่ไม่ได้รับประกันเหมือนกันทุกเครื่องหรืออนุมานว่าคำตอบถูกเสมอ โค้ดนี้ย่อ body จริงเพื่ออ่านบนสไลด์

หลักฐาน: robotIntent.ts: fetch / system prompt

## 15. Backend validation: ไม่เชื่อผลโมเดลอย่างเดียว

หลัง parse JSON มีการตรวจ Zod และตรวจรหัส POI ใน catalog จากนั้น service ตรวจคำปฏิเสธ กำกวม สิทธิ์และชื่อที่ผู้ใช้ระบุ อ่านแผนที่และพิกัดใหม่ก่อน dispatch และตรวจ freshness mapping localization และ lock คำหยุดยังตรวจ command epoch เพื่อกันผล AI ที่มาช้าสั่งเดินภายหลัง โค้ดด้านซ้าย excerpt สองส่วนจากไฟล์จริงจัดบรรทัดและตัดข้อความ error ให้สั้น

หลักฐาน: robotIntent.ts; robotAiService.ts; navigationPolicy.ts

## 16. ตัวอย่าง: ข้อความต่างสำนวนเลือก POI เดียวกัน

ตัวอย่างนี้อิงชื่อหน้าประตูที่มีหลักฐาน dry-run และชื่อเรียกทางเข้าที่รองรับใน metadata ถ้ามี alias อยู่จริง คำขอสุภาพสองแบบเข้าทางกฎ ส่วนข้อความที่วางจุดหมายก่อนคำขออาจใช้ LLM ผลคือ navigate_to กับรหัสเดียวกัน ข้อมูลด้านขวาเป็นรูปอธิบาย ไม่ใช่ log การทดลองใหม่ คำถามอยู่ไหนต้อง where_is ไม่เดิน และอย่าเพิ่งไปต้องไม่ dispatch

หลักฐาน: robotIntent.ts; scripts/check-kiosk-ai.mjs; reports/ai-benchmark/hybrid.json

## 17. ผล benchmark: วัดการตีความและ policy ร่วมกัน

ชุด regression มี 40 กรณีและ 6 POI fixture ตรวจ outcome และ target ที่คาดหวัง ผลวันที่ 7 ตุลาคม ก่อนปรับผ่าน 21/40 หลัง hybrid และ model เป็นหลักผ่าน 40/40 เสนอเดินผิดเจตนาหรือจุดหมายลด 4 เป็น 0 ในชุดนี้ เป็น dry-run บน PC และชุดที่ใช้พัฒนา ไม่ใช่ผล unseen หรือการเดินจริง hybrid ใช้กฎ 33 กรณี โมเดล 7 กรณี p95 4684 ms

หลักฐาน: reports/ai-benchmark/{baseline,hybrid,model}.json; docs/benchmark-ai.md

## 18. AI: งานที่ยังค้างอยู่

วิธีสามจะเพิ่ม pending intent และอายุของบริบทสำหรับคำตอบถามกลับหรือคำอ้างที่นั่น ต้องกันงานซ้ำและล้างเมื่อยกเลิก พร้อม benchmark แบบหลายข้อความ Jetson เตรียม source/model แล้วแต่ build พัก ไม่มี server และไม่มีผล benchmark ส่วน STT/TTS ยังไม่เปิดใช้ ทั้งหมดนี้เป็นงานถัดไป ไม่ใช่ความสามารถที่ทำเสร็จแล้ว

หลักฐาน: PROGRESS.md; SPEC.md; docs/jetson-ai.md

## 19. สรุปความคืบหน้า Website และ AI

สรุปฝั่ง Website มี Admin Robot Interface Backend แผนที่สดและ POI แล้ว ส่วน upload แก้แผนที่/กำแพงเสมือนและโหมดหุ่นยังค้าง ฝั่ง AI ทำ hybrid rules + LLM พร้อม JSON schema Zod validation และ backend checks แล้ว ผล regressionผ่าน 40/40 ในชุดพัฒนาบน PC งานต่อคือบริบท Jetson และเสียง เปิดรับคำถามและใช้ speaker notes อ้างตำแหน่งโค้ดได้

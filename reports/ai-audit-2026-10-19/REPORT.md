## โมเดลจริงแยกจากเว็บ

ทดสอบแบบ model-primary ผ่าน 5/6 กรณี: 5 กรณีเรียก Qwen จริง (ผ่าน 4 ไม่ผ่าน 1) และ 1 กรณีคำปฏิเสธถูกกฎบังคับดักไว้ก่อนเข้าโมเดล
การเรียกโมเดลใช้เวลาประมาณ 1.72–7.66 วินาทีในรอบนี้ เป็นชุดเล็ก ไม่ใช่คะแนนความแม่นยำ LLM โดยรวม

กรณีที่ผิด: “พาไปที่นั่น” โมเดลคืน intent=navigate_to, poiCode=null, confidence=0.95 และ needsClarification=false แทนที่จะขอชื่อจุดหมาย
นี่เป็นความไม่สอดคล้องเชิงความหมายที่ผ่านรูปแบบ JSON ได้ แต่ชั้นขอบเขตนำทางและตัวตรวจปลายทางยังปฏิเสธการเดินได้ รอบนี้ไม่ได้ dispatch งานใด

## สาเหตุที่พบ

1. ชุดทดลองเปิด Backend โดยไม่มี -LocalAI ทำให้ AI_MODE=off แม้ llama-server ที่พอร์ต 8080 จะ healthy คำขอที่ถึง handleRobotAiCommand จึงถูกปฏิเสธก่อนตัวจำแนกทำงาน
2. ai-status ให้ textReady=true เมื่อ navigationOnly=true แม้ modelReady=false จึงดูเหมือนพร้อมใช้งานทั้งที่บางคำขอไม่พร้อม
3. กฎใน streamKioskChat ส่งทุกข้อความที่ไม่เข้า request/location/status ไปข้อความแนะนำตัวเดียวกัน เช่น “ขอบคุณ”, “ลาก่อน”, “มีจุดหมายอะไรบ้าง” และข้อมูลอาคารที่ไม่มี
4. กฎ location ยังไม่ครอบคลุม “ช่วยบอกตำแหน่งห้องครัวหน่อย” และ “อยู่ชั้นไหน”; จึงถูก fallback ทักทายแทนตอบจากข้อมูลหรือแจ้งข้อจำกัด
5. โมเดลยังต้องมี semantic validation เพิ่มสำหรับ intent=navigate_to แต่ไม่มี POI แม้ confidence สูง

## ข้อเสนอแก้ไข (ยังไม่ได้ดำเนินการ)

- เปิด model connection ให้ตรงกับสถานะบนหน้าจอ และแยกความพร้อม Rules กับ LLM
- เพิ่มประเภท greeting / thanks / goodbye / list_destinations / staff_help / unsupported_building_info แทน fallback เดียว
- ตอบรายการจุดหมายและสถานะจากข้อมูลจริงโดยตรง ไม่ต้องพึ่ง LLM
- ตอบข้อมูลชั้น/เวลาเปิดว่าไม่มีข้อมูล เมื่อไม่มีฐานข้อมูลรองรับ
- ตรวจผล LLM เชิงความหมายและถามกลับเมื่อไม่มีปลายทาง ไม่ใช้ confidence เป็นสิทธิ์ให้เดิน
- นำประโยคที่พบในรอบนี้ไปเพิ่ม regression test ด้านคุณภาพคำตอบ; tests 58 รายการเดิมไม่ครอบคลุมกรณีเหล่านี้ทั้งหมด

# โน้ตช่วยพรีเซนต์ AI Robot Butler

สไลด์หลัก 1–16 ประมาณ 10–15 นาที; สไลด์ 17–18 สำรองสำหรับตอบคำถาม

เติมข้อมูลผู้จัดทำและอาจารย์ในสไลด์ 1 ก่อนนำเสนอ

## 1. ระบบหุ่นยนต์ผู้ช่วยและนำทางด้วย AI

แนะนำชื่อโครงงานและผู้จัดทำ ระบบนี้เชื่อมเว็บผู้ดูแลและเว็บผู้มาเยือนเข้ากับหุ่นผ่าน Backend และเพิ่ม AI local สำหรับคำขอภาษาธรรมชาติ เนื้อหาครั้งนี้อ้างอิงโค้ดและผลทดสอบที่บันทึกไว้ ไม่ได้ต่อหุ่นระหว่างจัดทำสไลด์ ตั้งใจใช้สไลด์หลัก 16 หน้าในเวลาประมาณ 10–15 นาที และอีก 2 หน้าเป็นข้อมูลสำรอง



## 2. ปัญหาที่โครงงานต้องการแก้

ปัญหาแรกคือผู้มาเยือนต้องการข้อมูลและจุดหมายที่ถูกต้อง ปัญหาที่สองคือเจ้าหน้าที่ต้องเห็นแผนที่และสถานะงานร่วมกัน ส่วนการใช้ AI มีความเสี่ยงตีความคำถามหรือคำปฏิเสธเป็นคำสั่ง จึงออกแบบให้ AI เสนอเจตนา และ Backend ตรวจอีกชั้นก่อนส่งงาน นี่เป็นโจทย์การออกแบบ ไม่ใช่ผลสำรวจผู้ใช้ที่เก็บแล้ว

หลักฐาน: SPEC.md; robotAiService.ts

## 3. เป้าหมาย: เว็บเดียวกันในระบบ สองกลุ่มผู้ใช้

เป้าหมายประกอบด้วยเว็บไซต์แยกสำหรับเจ้าหน้าที่และผู้มาเยือน การแสดงแผนที่และจัดการ POI การรับคำขอหลายสำนวน และการทดสอบก่อนทดลองเคลื่อนที่จริง จุดเน้นคือใช้รายการจุดหมายและข้อมูลจากหุ่นเป็นแหล่งอ้างอิง รวมทั้งตรวจงานและสิทธิ์ก่อนเริ่ม

หลักฐาน: PROGRESS.md; SPEC.md

## 4. สถาปัตยกรรม: Backend เป็นตัวกลาง

ลูกค้าสองเว็บไซต์ไม่สั่งหุ่นจากเบราว์เซอร์โดยตรง Admin ใช้ session และ Kiosk ใช้ token ผ่าน server-side proxy Backend เชื่อม PostgreSQL หุ่น และโมเดล Qwen ผ่าน llama-server โดยการค้นหา SearXNG เป็นบริการเสริม เส้นทางนี้ช่วยรวมการตรวจสิทธิ์ งาน และการบันทึกไว้ส่วนกลาง

หลักฐาน: apps/admin; apps/kiosk; apps/backend; packages/shared

## 5. แยกประสบการณ์ของเจ้าหน้าที่กับผู้มาเยือน

เจ้าหน้าที่มีบทบาท viewer, operator และ admin ส่วนผู้มาเยือนใช้ Kiosk และเลือกได้เฉพาะ POI ที่อนุญาต จุดที่ metadata.is_public เป็น false ถูกกรองออก Kiosk หยุดงานของตนเองได้ แต่หยุดงานที่มาจากเจ้าหน้าที่ไม่ได้ ข้อจำกัดตรวจใน Backend ไม่ได้อาศัยปุ่มที่ซ่อนบนหน้าจออย่างเดียว

หลักฐาน: routes/kiosk.ts; middleware/auth.ts; kioskHardwareAi.test.ts

## 6. แผนที่สดและ POI จากหุ่น

แผนที่กริดมี origin และ resolution ซึ่งต้องรักษาไว้เมื่อแสดงบนเว็บ รวมถึงค่าจุดกำเนิดติดลบ ระบบแสดงหุ่น แท่นชาร์จ LiDAR และ POI และรองรับซูมลาก การแก้ชื่อ พิกัด ทิศและ aliases ต้องอ่านข้อมูลกลับก่อนรายงานสำเร็จ ภาพบนสไลด์เป็นภาพอธิบาย ไม่ใช่ภาพแผนที่จริง ผลอ่านข้อมูลสดเป็นหลักฐานจากรอบที่เคยเชื่อมต่อ

หลักฐาน: LiveRobotMap.tsx; RobotMapEditor.tsx; hermesClient.ts; PROGRESS.md

## 7. ก่อนนำทาง ต้องผ่านข้อกำหนดของ Backend

การสั่งด้วย joystick ต้องถือ manual lock ที่มี TTL และ heartbeat การนำทางต้องมีแผนที่อายุไม่เกิน 5 วินาที อยู่ในโหมดระบุตำแหน่ง และมีคุณภาพอย่างน้อย 50 จุดหมายต้องอยู่ในแผนที่และเป็นพื้นที่ว่างตามค่าที่อ่าน หุ่นต้องไม่มีงานหรือ lock ขัดกัน มี halt และ E-Stop แต่พฤติกรรมหยุดจริงยังรอตรวจรับ โหมดกลับแท่นอัตโนมัติปิดไว้ในห้องแลป

หลักฐาน: navigationPolicy.ts; driver.ts; manualHardware.test.ts

## 8. AI ใช้สองวิธีร่วมกัน

วิธีแรกคือกฎรูปประโยคและชื่อเรียกอื่น เช่น ทางเข้าตรงกับ POI หน้าประตู ช่วยให้คำขอชัดเจนตอบเร็ว วิธีที่สองใช้โมเดลตีความประโยคอ้อมหรือจุดหมายที่อยู่ก่อนคำขอ โมเดลคืน JSON โดยจำกัดรหัสปลายทาง ความมั่นใจที่โมเดลรายงานไม่ใช่สิทธิ์ให้เดิน Backend ยังตรวจความหมายและสถานะหุ่น

หลักฐาน: robotLanguage.ts; robotIntent.ts; docs/benchmark-ai.md

## 9. AI เสนอคำสั่ง แต่ไม่ได้เลือกพิกัดอิสระ

อธิบายเส้นทางจากข้อความถึงงาน: อ่านรายการ POI ที่อนุญาต จำแนกเจตนา ตรวจ JSON schema ตรวจชื่อและความกำกวม แล้วอ่านพิกัดใหม่ก่อน dispatch การปฏิเสธหรือถามกลับไม่สร้างงาน dry-run คืนเพียงผลตีความ ส่วนงานจริงผ่านเงื่อนไขการนำทาง คำหยุดที่รองรับข้ามโมเดล และทำให้ผลที่กำลังรอ dispatch ภายหลังไม่ได้

หลักฐาน: robotAiService.ts; robotIntent.ts; robotAi.test.ts

## 10. ประโยคคล้ายกัน อาจต้องทำคนละอย่าง

ใช้ตัวอย่างแสดงความต่างของคำขอ คำถาม คำปฏิเสธและความกำกวม ชื่อห้องประชุมหรือห้องเล็กในสไลด์เป็นตัวอย่างจาก benchmark ไม่ได้ยืนยันว่าบนหุ่นปัจจุบันมีจุดเหล่านี้ คำถามตำแหน่งต้องตอบข้อมูล คำปฏิเสธไม่เดิน และชื่อกำกวมต้องถามใหม่ การเก็บคำตอบถามกลับข้ามข้อความยังเป็นงานถัดไป

หลักฐาน: benchmarks/robot-ai/cases.json; robotLanguage.test.ts

## 11. โหมดปกติ / โหมดสำรวจ: ตั้งค่าได้ขณะออฟไลน์

ตัวเลือกโหมดที่เพิ่มล่าสุดเป็น preference บนเว็บ บันทึกไว้ใน localStorage และเลือกได้เมื่ออุปกรณ์ไม่เชื่อมต่อ โหมดปกติหมายถึงแนวทางใช้แผนที่และ POI เดิม โหมดสำรวจเป็นตัวเลือกเตรียมสำรวจและสร้างแผนที่ แต่ยังไม่มี API เปลี่ยนโหมดจริง การเลือกหรือเชื่อมต่อใหม่ไม่ส่งคำสั่งและไม่เริ่มสำรวจอัตโนมัติ

หลักฐาน: RobotOperatingMode.tsx; PROGRESS.md 11 October 2026

## 12. ออกแบบ benchmark ให้ทดสอบโดยไม่เดิน

ชุด regression มี 40 ข้อความและ 6 POI fixture ทดสอบการจำแนกและ policy รวมกัน ให้ผ่านเมื่อ outcome และรหัสจุดหมายตรงกับ expected เปรียบเทียบ policy เดิม hybrid และ model เป็นหลัก Runner บังคับหุ่นจำลอง ฐานข้อมูล memory และ dry-run พร้อมจำกัด network เฉพาะโมเดล ไม่ใช้เป็นผลทดสอบการเดินจริง

หลักฐาน: benchmark-robot-ai.ts; cases.json; reports/ai-benchmark/*.json

## 13. ผล regression: จาก 21/40 เป็น 40/40

ผลที่รายงานบันทึกวันที่ 7 ตุลาคม 2569 ไม่ใช่การรันใหม่ในวันจัดทำสไลด์ policy เดิมผ่าน 52.5% และมี 4 กรณีเสนอเดินผิดเจตนาหรือจุดหมาย วิธี hybrid และ model เป็นหลักผ่านครบ 40 ในชุดนี้ แต่ชุดเดียวกันนี้ใช้พัฒนาด้วย จึงยังไม่ใช่ unseen evaluation และไม่รับประกันทุกประโยค ผลทั้งหมดเป็นข้อเสนอใน dry-run ไม่มีการส่งหุ่นเดิน

หลักฐาน: baseline.json; hybrid.json; model.json — 7 October 2026

## 14. หลักฐานที่ตรวจแล้ว และขอบเขตของผล

บันทึก Backend ผ่าน 51 tests และ typecheck ของ Admin Kiosk Backend ผ่าน มีการตรวจ Kiosk กับ POI จริงแบบ dry-run 4 สำนวนและเลือก UUID เดียวกัน การส่งงานถึง MoveTo ทดสอบผ่าน adapter จำลอง ส่วนการอ่านแผนที่และ LiDAR เป็นข้อมูลจากฮาร์ดแวร์ในรอบก่อนหน้า ไม่มีผลตรวจถึงจุดหมาย หยุดจริง หรือกลับแท่นจริงจากผู้ช่วย

หลักฐาน: PROGRESS.md; robotAi.test.ts; kioskHardwareAi.test.ts; check-kiosk-ai.mjs

## 15. ข้อจำกัดปัจจุบัน และงานที่ควรทำต่อ

ปัจจุบัน AI ทำงานบนพีซี Jetson เตรียมอุปกรณ์และโมเดลแล้วแต่ build พักและไม่มี benchmark บนอุปกรณ์ ระบบเสียงยังไม่เปิด บริบทถามกลับเช่นห้อง A หรือที่นั่นข้ามข้อความยังไม่ทำ โหมดสำรวจเป็น preference ฝั่งเว็บ ขั้นต่อไปควรเพิ่มการถามกลับแบบมีอายุ ทดสอบหลายข้อความ แล้วเชื่อมโหมดจริงและตรวจรับการเดินในพื้นที่ที่ผู้ใช้ควบคุม

หลักฐาน: PROGRESS.md; SPEC.md; docs/jetson-ai.md

## 16. เว็บ + ข้อมูลจริง + AI ที่ผ่านการตรวจคำขอ

สรุปว่าโครงงานรวมเว็บผู้ดูแล จอผู้ช่วย ข้อมูลแผนที่ และ AI local โดยตรวจคำขอผ่าน Backend ก่อนสร้างงาน ผล regression ดีขึ้นในชุดที่ทดสอบ แต่ยังไม่ปิดงานตรวจรับหน้างาน เปิดให้กรรมการถามเรื่องสถาปัตยกรรม policy ความกำกวม ความเร็ว หรือ Jetson ใช้สไลด์สำรอง 17 และ 18 ประกอบคำตอบได้



## 17. ข้อมูลสำรอง: ความหน่วงและข้อจำกัดการวัด

ตอบคำถามเรื่องเวลา: hybrid ใช้กฎ 33 กรณีและโมเดล 7 กรณี จึง median ที่ปัดเป็น 0 ms หมายถึงต่ำกว่า 0.5 ms ส่วน p95 ประมาณ 4.684 วินาที วิธี model ใช้โมเดล 30 กรณีและกฎ 10 กรณี รอบนั้นมี Kiosk ร่วมช่วงต้น จึงมี queue ที่อาจกระทบเวลา ไม่ควรเปรียบเทียบประสิทธิภาพแบบควบคุมทุกตัวแปร ไม่ได้วัด RAM peak, TTFT, Jetson หรือการเดินจริง

หลักฐาน: reports/ai-benchmark/{baseline,hybrid,model}.json; docs/benchmark-ai.md

## 18. ข้อมูลสำรอง: เอกสารและไฟล์อ้างอิง

แหล่งข้อมูลหลักคือโค้ดและหลักฐานของโครงการ รายงานรูปเล่มและ JSON benchmark สามารถเปิดตรวจรายกรณีได้ เอกสารผู้ผลิตและ model card ใช้เป็นแหล่งเทคโนโลยีประกอบ ไม่ใช้ชื่อบุคคลหรือผลการทดลองจากเล่มตัวอย่าง หากกรรมการต้องการผลการเดินจริงให้แจ้งว่ายังเป็นรายการรอตรวจรับ

หลักฐาน: reports/project-documentation; PROGRESS.md; repository source

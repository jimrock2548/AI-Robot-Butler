# ผลทดสอบเคลื่อนที่จริงแบบมีผู้ดูแล — 21 ตุลาคม 2569

ผู้ใช้ระบุว่า POI “หน้าประตูห้อง” ใช้ทดสอบได้และสามารถหยุดหุ่นได้ จึงดำเนินการกับ Hermes จริงตามเส้นทางนี้เท่านั้น ใช้ความเร็ว **0.10 m/s / 0.30 rad/s** ตรวจลิงก์ คุณภาพตำแหน่งอย่างน้อย 50 งานค้าง และ action จากอุปกรณ์อื่นก่อนเริ่ม ไม่สุ่มไปจุดอื่นในแล็บ

## ปัญหาที่พบและแก้

**หน้าเว็บแสดงออนไลน์ค้างเมื่อเครือข่ายของแท็บขาด:** พบจริงจากการตั้ง Chrome offline หลัง 8.5 วินาทีข้อมูลเก่าแต่ป้ายยังออนไลน์ แก้ให้คำนวณอายุข้อความในเบราว์เซอร์ด้วยนาฬิกาฝั่ง client: 2 วินาทีเป็น stale และ 5 วินาทีเป็น dead โดยไม่ปรับสถานะเสียจาก Backend ให้ดีขึ้นเอง เมื่อรับข้อความสดจึงกลับออนไลน์ ทดสอบซ้ำผ่านทั้ง offline และ reconnect คงข้อมูลตำแหน่งล่าสุดและสถานะ E-Stop ไว้

หลักฐาน: [ผล client disconnect/reconnect](client-disconnection.json), [ภาพขณะลิงก์ขาด](client-offline.png)

**เพิ่ม POI ชั่วคราวถูกปฏิเสธ:** หุ่นตอบ `HTTP 403` ที่ `POST /api/core/artifact/v1/pois` ขณะหุ่นว่างและอยู่โหมดปกติ จึงไม่มีจุดใหม่ถูกเพิ่ม ไม่ลบ/แก้จุดจริงเพื่อเลี่ยงข้อจำกัด เปลี่ยนการทดลองจุดประจำไปใช้ POI หน้าประตูเดิมแทน แก้ Backend ให้ส่ง `poi_write_failed` พร้อมสาเหตุ 403 แทนข้อความ 500 ทั่วไป สาเหตุฝั่ง firmware ยังไม่ยืนยัน ไม่อ้างว่าเป็นจำนวนจุดสูงสุดหรือ license จากข้อมูลเพียงเท่านี้ รอบก่อนเคยทดสอบ POI CRUD ผ่านขณะมีจุดน้อยกว่า แต่ผลนั้นไม่ยืนยันว่ากรณีนี้ผ่าน

## สถานะหลังจบ

คงหุ่นใน **E-Stop ใกล้หน้าประตูห้อง** ไม่สั่งเดินต่อหรือปลดเอง Backend ไม่มีงานค้าง ลิงก์ปกติ ตั้งความเร็วทดสอบ 0.10 m/s / 0.30 rad/s ค้างไว้ ค่าที่ผู้ใช้ตั้งก่อนทดสอบคือ 0.50 m/s / 0.60 rad/s เก็บในผล JSON แต่ไม่เพิ่มความเร็วหรือแก้ตั้งค่าขณะ E-Stop ค้าง

หลัง E-Stop อ่าน robot health จริงได้ hasSystemEmergencyStop=true และข้อความ “system emergency stop” เป็นสถานะที่ตั้งใจทิ้งไว้จากการทดสอบ ไม่ใช่การขาดการเชื่อมต่อ การตั้งจุดประจำชั่วคราวคืนเป็นค่าก่อนทดสอบแล้ว ไม่มีการลบ POI เดิม

ดู [สถานะสุดท้ายและรายชื่อ POI](final-snapshot.json) หากจะทดสอบเดินต่อ ผู้ควบคุมต้องตรวจพื้นที่แล้วปลดหยุดฉุกเฉินผ่านหน้าควบคุมหรือตัวหุ่นตามสภาพจริงก่อน

## การตรวจซอฟต์แวร์

- Backend **72/72 tests ผ่าน** รวม regression สำหรับ client ที่ไม่ได้รับข้อความใหม่
- Typecheck ผ่าน Backend, Admin และ Robot Interface
- Production build ทั้งระบบผ่านหลังแก้ไข
- สคริปต์ `check-supervised-motion.mjs` ต้องมี `--execute` และทดสอบทีละ case ใช้เฉพาะเส้นทางหน้าประตูที่ได้รับอนุญาต มีขอบเขตระยะ/เวลาและยกเลิกเมื่อสถานะผิดปกติ ไม่ควรรันซ้ำโดยไม่มีผู้ดูแลอยู่กับหุ่น

## รายการที่ยังไม่ผ่านหรือยังทำไม่ได้

1. **เสียงจริง/Wake word/ไมค์และข้อความเจ้าหน้าที่ที่พูดออกลำโพง:** ส่งคำถามให้ผู้ใช้ทดสอบบนอุปกรณ์จริงแล้ว ยังรอผล การตรวจ Chrome headless ก่อนหน้านี้พบ synthesis-failed และไมค์ยังเป็น prompt ดู [รายงานเสียง](../remaining-tests-2026-10-21/REPORT.md) ไม่อ้างว่าเสียงผ่านจากการเดินผ่าน
2. **เพิ่ม POI ที่หุ่นตอบ 403:** ยังต้องตรวจสาเหตุและสิทธิ์ฝั่ง firmware ตามข้างต้น
3. **เครือข่าย Backend ↔ หุ่นขาดจริง:** เตรียมสคริปต์ให้บล็อกเฉพาะ TCP 192.168.1.63:1448 ชั่วคราวขณะ E-Stop ค้าง แล้วคืนกฎอัตโนมัติ แต่ Windows ปฏิเสธ New-NetFirewallRule ด้วย Access denied แม้รันนอก sandbox กฎไม่ได้ถูกสร้างและเครือข่ายหุ่นไม่ได้ถูกตัด ผลที่ผ่านรอบนี้เป็นการขาดเครือข่ายเฉพาะ client เท่านั้น ดู [preflight](robot-link-loss.json)
4. **แผนที่ต่างสถานที่และการเดินสำรวจพื้นที่ใหม่:** ยังไม่มีแผนที่/พื้นที่ที่สองที่ยืนยันพร้อมใช้ ไม่สั่งออกนอกเส้นทางหน้าประตูที่ได้รับอนุญาต ทดสอบเปิด–ปิด mapping และโหลดแผนที่เดิมไว้แล้ว
5. **รีสตาร์ตหุ่นและตรวจการคงข้อมูล:** ยังไม่ทำ ไม่ปลด E-Stop หรือรีสตาร์ตอุปกรณ์ต่อเองหลังการทดสอบหยุด
6. **คลิปหน้างาน/ตรวจรับกับพี่ปลั๊ก และ Jetson:** ยังไม่ได้ดำเนินการ ไม่มีการนำ telemetry มาอ้างว่าเป็นคลิปภาพหุ่นจริง

ดังนั้นผลนี้ปิดการทดสอบเคลื่อนที่หลักในเส้นทางที่อนุญาตได้ แต่ **ยังไม่ใช่การตรวจครบทุกฟังก์ชันของโครงการ**
